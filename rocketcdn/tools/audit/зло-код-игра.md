## НАХОДКИ

### 1. Одно переключение языка при закрытом полёте — и голограммы над телами/узлами исчезают насовсем до перезагрузки страницы
Файлы: `assets/rc-flight.js:5423-5426` (`holoReady`, `holoSetup`), `assets/rc-flight.js:170-196` (`relang`), `assets/rc-flight.js:870-873` (`ui.wrap`/`ui.hud`), `assets/rc-holo.js:143-146` (`init`).

`holoSetup()` вызывает `g.RC_HOLO.init(...)` РОВНО ОДИН РАЗ за всю жизнь страницы — флаг-защёлка модульного уровня, не привязанная к конкретному DOM-узлу:
```
5423  var holoReady = false, holoIds = {};
5424  function holoSetup() {
5425    if (holoReady || !g.RC_HOLO || !ui.wrap) return;
5426    holoReady = true;
...
5430    g.RC_HOLO.init(ui.hud || ui.wrap);
```
`ui.hud` — это дочерний узел `ui.wrap` (`873: ui.hud = w.querySelector(".rcf-hud");`, где `w` тут же и есть `ui.wrap`, `870: ui.wrap = w;`). `rc-holo.js` кладёт свой слой меток `LAYER` именно внутрь переданного узла и держит на него единственную живую ссылку — переинициализация тоже защищена: `init()` создаёт `LAYER` заново, только если его вообще не было или он висит в другом родителе, но ничего не проверяет на «узел вообще ещё в документе»:
```
143  function init(host) {
144    var parent = host || doc.body;
145    if (LAYER && LAYER.parentNode === parent) return LAYER;
```
А вот `relang()` — обработчик смены языка сайта, срабатывающий при закрытом полёте, — сносит весь `ui.wrap` (а с ним и `ui.hud`, и вложенный в него `LAYER`) из DOM и ничего не знает про `holoReady`:
```
189    if (ui.wrap.parentNode) ui.wrap.parentNode.removeChild(ui.wrap);
190    ui = {};
```
`holoReady` при этом не сбрасывается нигде в файле — единственное место, где он становится `false` снова, это `catch` в самом `holoSetup()` при ошибке инициализации (строка 5465), к смене языка не имеющее отношения.

**Путь в игре:** открыть полёт → закрыть крестиком (пока открыт, объекты `ui.wrap/ui.hud` и старый `LAYER` живы, `holoReady === true`) → переключить язык сайта RU↔EN — обычное действие в шапке → `relang()` видит `F.open === false`, реально выполняет снос: `ui.wrap` со всем поддеревом (включая старый `.rc-holo` слой) удаляется из документа, `ui` обнуляется → открыть полёт снова: `buildUI()` пересобирает всю разметку с нуля, новый `ui.hud` — уже другой, живой DOM-узел, но `holoFrame()` на каждом кадре продолжает звать `holoSetup()`, а тот молча выходит по `if (holoReady) return;` и НИКОГДА не передаёт новый `ui.hud` модулю голограмм. `RC_HOLO.add()`/`place()` продолжают писать метки в старый, отсоединённый от документа узел `LAYER` — он существует в памяти, полностью функционален программно (можно дергать его API без ошибок), но не отрисовывается, потому что не является частью дерева документа.

Результат: подписи над планетами, спутником, поставленными узлами сети и голограмма курса, которые должны появляться в кабине («ЛУНА», «МАРС», карточка узла) — не показываются больше ни разу за сессию, без единой ошибки в консоли. Клик по несуществующей (невидимой) метке точно так же не срабатывает — RC_HOLO.onPick никогда не долетает от невидимого слоя. Всё это чинится только полной перезагрузкой страницы, поскольку `holoReady` — module-scoped переменная без внешнего сброса.

### 2. Тот же цикл смены языка — и вся светящаяся панель приборов (кнопки, радар, шкалы) остаётся невидимой, потому что холст больше не в документе
Файлы: `assets/rc-flight.js:8521` (`var deck = null;`), `assets/rc-flight.js:8524-8532` (`deckLayer`), `assets/rc-flight.js:189-190` (`relang`, снос `ui.wrap`).

Ровно тот же класс дефекта, что и в находке 1, но в другом модуле — приборной панели. Холст с подсветкой клавиш, шкал и радара создаётся и подшивается в DOM один-единственный раз за всю жизнь страницы:
```
8521  var deck = null;
...
8524  function deckLayer() {
8525    if (!ui || !ui.wrap || !g.RC_DECK || !g.RC_CAB_FLAT || !g.RC_CAB_DECK) return null;
...
8530    if (!deck) {
8531      deck = g.RC_DECK.создать();
8532      ui.wrap.appendChild(deck.canvas);
8533    }
```
`grep -n "deck.canvas"` по всему файлу находит это `appendChild` ровно один раз — больше нигде холст `deck.canvas` в документ не вставляется. Переменная `deck` объявлена на уровне модуля и не сбрасывается ни в `close()`, ни в `relang()`.

**Путь в игре:** тот же, что в находке 1 — открыть полёт (первый вызов `deckLayer()` создаёт `deck` и подшивает его холст к текущему `ui.wrap`) → закрыть → переключить язык сайта, пока полёт закрыт → `relang()` сносит `ui.wrap` целиком, включая уже подшитый в него `deck.canvas` (`189-190`) → открыть полёт снова: `buildUI()` собирает новый `ui.wrap`, но `deckLayer()` видит, что модульная переменная `deck` уже не `null` (осталась от прошлого раза), пропускает ветку `if (!deck)` целиком и НЕ подшивает холст к новому `ui.wrap`. Дальше `deck.кадр()` продолжает честно рисовать на холсте каждый кадр — рисунок существует, у него правильные данные, `deck.попал(x,y)` по-прежнему возвращает верный индекс клавиши под курсором, — но сам `<canvas class="rcf-instr">` висит вне документа и на экран не попадает ни пикселем.

Итог: после смены языка и повторного входа панель управления выглядит голым металлом без единого намёка на подсветку клавиш, шкалу тяги, радар и подписи команд — при том что сами DOM-кнопки (`ui.deploy`, `ui.scanKey` и т.д.) продолжают физически работать, потому что они отдельные элементы, а не часть холста. Разрыв между «кнопка нажимается» и «на кнопке ничего не нарисовано» читается как полностью сломанный пульт.

Рядом та же болезнь бьёт и по самим зонам нажатия объёмных клавиш. `physicalControlsFrame()` (строка 5837) каждый кадр проецирует 3D-крышки клавиш в экранные координаты и пишет их в `--rcf-phys-x/y/w/h` у соответствующих DOM-кнопок — но список этих кнопок тоже собирается один раз и держится в той же незасбрасываемой обёртке функции:
```
5838  if (!physicalControlsFrame.nodes) {
5839    physicalControlsFrame.nodes = [
5840      ui.wrap.querySelector(".rcf-navkey"),
...
```
`deckFrame()` (строка 8559) читает и заполняет ТУ ЖЕ САМУЮ `physicalControlsFrame.nodes` — общий кэш на оба режима пульта. После того же цикла «открыл → закрыл → сменил язык → открыл» этот массив продолжает указывать на кнопки старого, уже удалённого `ui.wrap`: именно они получают свежие `--rcf-phys-x/y/w/h` и класс `rcf-phys-hit`, а новые настоящие кнопки в текущем `ui.wrap` этот класс и позиционирование не получают никогда. Судя по CSS (`assets/rc-flight.css:4438` и соседние правила `.rc-flight .rcf-deck .rcf-phys-hit`), именно класс `rcf-phys-hit` задаёт кнопке видимый размер и положение поверх ниши/крышки клавиши в этом режиме пульта — без него кнопка либо не позиционирована вообще, либо не совпадает с нарисованной клавишей, то есть зона нажатия и то, что нарисовано под ней, расходятся ещё и в этом слое, вдобавок к пропавшей подсветке из абзацев выше.

### 3. Переключение языка при закрытом полёте плодит дубликаты глобального keydown — повторный вход и стрелка вверх/вниз/пробел разгоняют корабль сильнее одного нажатия
Файлы: `assets/rc-flight.js:170-196` (`relang`), `assets/rc-flight.js:489` (`buildUI`), `assets/rc-flight.js:1141` (вызов `bindControls()` внутри `buildUI`), `assets/rc-flight.js:4921-4926` (регистрация `keydown`).

`buildUI()` защищена от повторной сборки только пока жив `ui.wrap`:
```
489  function buildUI() {
490    if (ui.wrap) return;
```
`bindControls()` вызывается последней строкой внутри неё (`1141: bindControls();`) и там же, глобально на `window`, вешается обработчик клавиатуры:
```
4921  addEventListener("keydown", function (e) {
4922    if (!F.open) return;
4923    if (e.key === "Escape") { close(); return; }
4924    if (e.key === "ArrowDown" || e.key === "PageDown" || e.key === " ") { F.v += 0.14; e.preventDefault(); manual(); }
4925    if (e.key === "ArrowUp" || e.key === "PageUp") { F.v -= 0.14; e.preventDefault(); manual(); }
4926  });
```
и следом `pointerup`/`resize` — тоже глобальные, тоже без `removeEventListener`.

А вот `relang()`, которая срабатывает на смену языка сайта (`rc:lang`), при закрытом полёте не просто перерисовывает интерфейс — она сносит весь `ui.wrap` из DOM и обнуляет `ui`:
```
170  function relang() {
171    RU = doc.documentElement.lang !== "en";
172    if (F.open) { langDirty = true; return; }
...
189    if (ui.wrap.parentNode) ui.wrap.parentNode.removeChild(ui.wrap);
190    ui = {};
```
Комментарий рядом объясняет, зачем сносить DOM (мир нарисован в старый холст), но нигде при этом не снимаются три window-обработчика, поставленные `bindControls()` — `removeEventListener` для `keydown`/`pointerup`/`resize` в файле нет вообще (`grep -c removeEventListener` находит только 2 вхождения на весь файл, оба относятся к событию `rc:3d`, не к этим трём).

**Путь в игре:** открыть полёт кнопкой «Полёт» → закрыть крестиком (F.open=false, `ui.wrap` остаётся в DOM, просто без класса `on`) → переключить язык сайта (RU↔EN) — это обычное действие в шапке, а не выброшенный сценарий → `relang()` видит `F.open===false`, сносит `ui.wrap`, обнуляет `ui` → открыть полёт снова: `buildUI()` видит пустой `ui.wrap` и пересобирает интерфейс с нуля, включая повторный вызов `bindControls()` — второй набор `keydown`/`pointerup`/`resize`-обработчиков вешается НА ТОТ ЖЕ `window`, старый никуда не делся.

Повторить цикл «закрыл → сменил язык → открыл» ещё раз — уже три живых `keydown`-обработчика. Все они читают общий `F.v` и `F.open` из замыкания на внешние переменные (это не локальные копии), поэтому не гасят друг друга: одно нажатие ArrowDown/Space внутри полёта выполняет `F.v += 0.14` N раз подряд (по числу накопленных дублей), корабль дёргается вперёд/назад заметно сильнее одного нажатия, а Escape вызывает `close()` N раз (здесь безвредно, `close()` сама проверяет `if (!F.open) return`, но исполняется N раз впустую). `resize` аналогично гоняет `size()`/`cabSrc()` N раз на каждое изменение окна.

Обычный пользовательский путь — попробовать полёт, закрыть, переключить язык сайта на английский (или обратно), открыть полёт снова — это стандартная последовательность действий на сайте, не эксплойт.

### 4. Развёртывание узлов и трафик сети не освобождают geometry/material/texture у three.js — растущая утечка GPU-памяти за одну игровую сессию
Файлы: `assets/rc-flight.js:5246` (`netLine`), `assets/rc-flight.js:5294` и `assets/rc-flight.js:6586` (`netBeam`), `assets/rc-flight.js:7655` (`traf`), `assets/rc-flight.js:2542-2550` (`glowSprite`).

`netMark()` при каждом развёртывании узла (со второго узла в сети) выбрасывает старую линию связи и строит новую, не освобождая ресурсы старой:
```
5245    if (netNodes.length > 1) {
5246      if (netLine) W3.scene.remove(netLine);
5247      var pts = [];
...
5258      var geo = new g.THREE.BufferGeometry().setFromPoints(pts);
5259      netLine = new g.THREE.LineSegments(geo, new g.THREE.LineBasicMaterial({...}));
```
`W3.scene.remove(netLine)` убирает объект из сцены, но не вызывает `geo.dispose()`/`material.dispose()` у старого `netLine` — тот же паттерн у луча развёртывания:
```
5294  if (netBeam) W3.scene.remove(netBeam);
5295  var geo = new T.BufferGeometry().setFromPoints([...]);
5296  netBeam = new T.Line(geo, new T.LineBasicMaterial({...}));
```
и у визуализации трафика между узлами, которая пересобирается в `trafBuild()` при каждом деплое узла и при каждой потере узла в аварии (`failTick`, до узла раз в 46-64 секунды, пока в сети есть что ронять):
```
7655  if (traf) { W3.scene.remove(traf); traf = null; }
...
7666  traf = new T.Points(geo, new T.PointsMaterial({
7667    ...
7668    map: glowSprite(32, "rgba(220,245,255,1)", "rgba(120,200,240,0)"),
```
`glowSprite()` при каждом вызове создаёт НОВЫЙ `<canvas>` и НОВУЮ `THREE.CanvasTexture`:
```
2542  function glowSprite(size, inner, outer) {
2543    var c = doc.createElement("canvas");
...
2550    return new g.THREE.CanvasTexture(c);
2551  }
```
Ни у `netLine`, ни у `netBeam`, ни у `traf` при замене не вызывается `.geometry.dispose()`, `.material.dispose()` или `.material.map.dispose()` — во всём файле `grep -n "\.dispose("` находит только один вызов, и тот относится к рендереру при смене языка (строка 182), не к этим объектам.

**Путь в игре:** долететь до тела, развернуть узел (кнопка УЗЕЛ на пульте) минимум дважды за сессию — уже пересборка `netLine`; каждое следующее развёртывание пересобирает и `netBeam`, и (через `trafBuild()`, вызываемый из `deployNode()`) `traf` вместе с новой текстурой из `glowSprite()`. При достаточно долгой игре в сети появляются аварии (`failTick`), и каждая потеря узла из сети (`net`) тоже вызывает `trafBuild()` — то есть даже без новых развёртываний геометрия и текстура трафика пересобираются заново при каждой аварии. Ни разу выброшенные буферы и канвас-текстуры не освобождаются explicit — держит их только сборщик мусора JS, который для WebGL-ресурсов (буферы, текстуры на GPU) ничего не освобождает сам: `dispose()` обязателен именно для three.js-объектов. За одну игровую сессию с несколькими узлами и парой аварий счёт неосвобождённых `BufferGeometry`/`Material`/`CanvasTexture` идёт на десятки.

## ПОДОЗРЕНИЯ (не доказано)

- `assets/rc-flight.js:200-201` — `doc.addEventListener("rc:lang", relang); addEventListener("rc:lang", relang);`. Событие `rc:lang` рассылается в `assets/rc-app.js:199` через `document.dispatchEvent(new CustomEvent("rc:lang", {...}))` без `bubbles:true` (default `bubbles:false`), поэтому оконный обработчик (вторая строка, на `window`) в обычном браузере никогда не должен получить это событие — событие адресовано только `document`. Похоже на мёртвый, но безвредный код (второй листенер просто никогда не срабатывает, `relang()` не выполняется дважды). Не проверял вживую движком событий, полагаюсь на спецификацию DOM про `bubbles`.
