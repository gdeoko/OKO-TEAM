# Cron-автоматизации сайта КЦ «Музыкальный Мир»

Все задания лежат в `cron/*.php`. Каждый файл - самостоятельный CLI-скрипт: сам
подключает фундамент (`config.php` + нужные `core/*.php`), точно так же, как
`scripts/test_generators.php`. Общая утильная библиотека для самих cron-заданий -
`cron/_lib.php` (логирование, файловые локи, идемпотентность через `audit_log`,
уведомление внешнего агента, загрузка в S3, ротация старых файлов). Она **не**
относится к `core/` - это не публичный контракт фундамента сайта, просто общий
код для файлов из `cron/`.

## Как поставить

1. Скопировать пути и подставить их в `scripts/crontab.txt` (`$APP`, `$PHP`).
2. `crontab -e` и вставить содержимое `scripts/crontab.txt` (или
   `crontab scripts/crontab.txt`, если больше ничего в crontab пользователя нет).
3. Убедиться, что у пользователя, от имени которого крутится cron, есть права на
   запись в `data/`, `data/logs/`, `data/backups/`, `public/posters/`.
4. Проверить руками перед постановкой в cron: `php cron/<файл>.php` - каждый
   скрипт безопасен для повторного запуска (идемпотентен) и не падает на пустой
   БД (только что созданной, без данных).

Часовой пояс: `config.php` вызывает `date_default_timezone_set('Europe/Moscow')`,
поэтому все PHP-таймстампы, которые пишет код проекта руками (`sent_at`,
`last_login`, `published_at` и т.п.), - в московском времени. Если у сервера
системный TZ отличается от Europe/Moscow, часы в `scripts/crontab.txt` нужно
пересчитать под системный TZ (сам cron ориентируется на системное время).

## Задания

### `process_newsletter_queue.php` - каждую минуту
Отправляет пачку писем из `mail_queue` (`status='queued'`), размер пачки -
`cfgv('mail_batch_size')`, с учётом суточного лимита `cfgv('mail_daily_limit')`
(Gmail SMTP). Если подключён `core/newsletter.php` с функцией
`newsletter_process_queue(int $limit): int` - вся отправка делегируется ей
(движок рассылок с A/B, трекингом открытий/кликов и отпиской). Иначе - простая
отправка через `mail_send()` с проставлением `status=sent|failed`, `tries++`.

### `send_reminders.php` - раз в день
Кладёт в `mail_queue` три вида напоминаний (реальную отправку потом делает
`process_newsletter_queue.php`):
- **Оплата** - платный конкурс, заявка не оплачена, старше 2 суток, не отклонена.
- **Награды** - у заявки есть результат, прошло от 3 дней после `results_date`
  конкурса, но заказа в `awards_orders` ещё нет.
- **Дедлайн** - активным подписчикам (`subscribers`), когда до `end_date`
  открытого конкурса остаётся 5, 3 или 1 день.

Каждое напоминание разовое: факт отправки фиксируется в `audit_log`
(`already_notified()` в `cron/_lib.php`), повторный запуск в тот же день не
дублирует письма.

### `check_competitions_dates.php` - раз в день
- Автозакрытие: `competitions.status='open'` и `end_date` уже прошёл -
  `status='closed'`.
- Генерация афиш `poster_generate()` (`core/poster.php`) по типам: `open`
  (в 3 форматах - 1x1/16x9/9x16, для открытых конкурсов), `5days`/`3days`/`lastday`
  (по числу дней до `end_date`), `results` (после наступления `results_date`).
  Каждая афиша - одна строка в таблице `posters`; при повторном запуске
  проверяется, нет ли уже такой строки (competition_id+type+format), поэтому
  дублей не возникает.
- Уведомление внешнего мозг-агента (`cfgv('agent_url')`, если задан) о закрытии
  конкурса и о готовности новой афиши.

### `publish_scheduled_posts.php` - раз в час
Забирает из `posters` афиши с `published_at IS NULL` («отложенные посты») и
отправляет их внешнему агенту (`cfgv('agent_url')`, событие `publish_poster`) -
предполагается, что дальше агент публикует их в соцсети КЦ. При успешном ответе
агента `published_at` проставляется, повторно афиша не отправляется. Если
`agent_url` не задан или агент недоступен - афиша остаётся в очереди до
следующего часового запуска.

### `daily_backup.php` - раз в день (ночью)
Согласованный снимок `data/muzmir.sqlite` через `VACUUM INTO` (безопасно даже
при активной записи в WAL). Локальная копия всегда сохраняется в
`data/backups/` (ротация 30 дней). Если заданы ключи S3 (env
`S3_ACCESS_KEY`/`S3_SECRET_KEY`, либо `OKO_S3_ACCESS_KEY`/`OKO_S3_SECRET_KEY`,
либо `cfg('MUZMIR_S3_ACCESS_KEY'/'MUZMIR_S3_SECRET_KEY')` в `config.local.php`) -
копия дополнительно грузится в S3-совместимое хранилище Timeweb Cloud
(`s3.twcstorage.ru`, бакет по умолчанию `muzmir-backups`, переопределяется
`S3_BUCKET`/`OKO_S3_BUCKET`/`MUZMIR_S3_BUCKET`). Без ключей - только локальная
копия, как и требуется.

### `weekly_backup.php` - раз в неделю
Полный дамп: БД (тот же `VACUUM INTO`) + `public/uploads/` + `public/diplomas/`
в один zip-архив в `data/backups/` (ротация 90 дней). Тот же принцип
локально-всегда + S3-если-есть-ключи, что и в `daily_backup.php`.

### `health_check.php` - каждые 5 минут
Self-ping на `cfgv('base_url')`. При недоступности - `tg_notify_admin()`, но
только при смене состояния (было доступно -> стало недоступно), чтобы не
спамить админа каждые 5 минут; при восстановлении - отдельное уведомление.
Состояние хранится в `settings` (`health_last_state`).

### `monthly_report.php` - 1-го числа месяца
Сводка за предыдущий календарный месяц (заявки, оплаты, заказы наград,
регистрации, новые подписчики, топ-5 конкурсов по числу заявок) -
`tg_notify_admin()` + письмо на `cfgv('org_email')` через `mail_queue`.
Идемпотентно: `settings.monthly_report_last` хранит месяц последнего отправленного
отчёта, повторный запуск в этом же месяце ничего не делает.

## Ключи S3 (для `daily_backup.php` / `weekly_backup.php`)

Ищутся в таком порядке (см. `s3_cfg()` в `cron/_lib.php`):
1. `env S3_<NAME>` (например, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET`).
2. `env OKO_S3_<NAME>`.
3. `cfg('MUZMIR_S3_<NAME>')` из `config.local.php` (в git не хранится).
4. Иначе - дефолт (`ENDPOINT=s3.twcstorage.ru`, `REGION=ru-1`,
   `BUCKET=muzmir-backups`) либо, для ключей доступа, «S3 не готов» и
   тихий фолбэк только на локальную копию.

Загрузка - подпись AWS SigV4 (PUT), реализована в чистом PHP (`curl` +
`hash_hmac`), без внешних SDK.

## Проверка

```
php -l cron/<файл>.php     # синтаксис
php cron/<файл>.php        # ручной прогон на текущей БД (см. data/muzmir.sqlite)
```

Все восемь скриптов проверены прогоном на сидовой БД (`scripts/seed_demo.php` /
`db_seed()` из `core/seed.php`) - без фаталов, включая повторные запуски подряд
(идемпотентность). Логи - `data/logs/cron.log` (свои сообщения) и
`data/logs/mail.log` (то, что пишет `core/mailer.php`/`core/newsletter.php`).
