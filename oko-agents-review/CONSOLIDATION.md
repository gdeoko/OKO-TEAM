# Карта сведения трёх треков «ОКО»

Сейчас параллельно живут три разных «ОКО». Они пересекаются по данным
(лиды, оплаты, анкеты) и по бренду, но не сведены — риск дублировать
работу и данные. Ниже — что это, и предлагаемое разделение ролей.

## Что есть

| Трек | Где | Стек | Статус | Роль |
|------|-----|------|--------|------|
| **A. okoteam.top** | загруженные `api.php`, `polling.php`, `cron.php`, `admin`, лендинги | PHP + плоские JSON-файлы | 🟢 работает в проде | Витрина + приём лидов/оплат/анкет |
| **B. oko-agents** | 3 zip (part1/CODE/VAULT) | Python 3.11, Pyrogram, Claude API, SQLite, Flask | 🟡 ТЗ + скелет ~10-15% | Автономный агент-продажник (парсинг вакансий → отклик → диалог → КП/договор → оплата) |
| **C. oko-app** | `CLAUDE.md`, Supabase проект `tkjewndtlzhnmqwmrnil` (28 таблиц), higgsfield-ссылка | Supabase + Fastify (`oko-app/server`) + прототип HTML | 🟡 инфра развёрнута, прототип на публичной ссылке | Продукт «Система роста» как приложение (Волна 1 — 15 июля) |

## Конфликты, которые надо развести

1. **Три хранилища данных о клиентах:**
   - A пишет в `data.json` / `anketas.json` (плоские файлы, гонки, PII в открытом виде);
   - B проектирует свою SQLite (`database/models.py`, 28 таблиц);
   - C уже имеет Supabase с 28 таблицами.
   → **B и C описывают одни и те же 28 таблиц.** Держать две БД нет смысла.

2. **Два бота/токена, два набора «аккаунтов Telegram».**
3. **Анкета есть и в A (`sistemaanketa.html` + `saveAnketa`), и в B (`anketa/` 25 вопросов), и в C.**

## Предлагаемое решение (одна архитектура)

**Единый источник данных — Supabase (трек C).** Он уже развёрнут, 28 таблиц,
не плоские файлы, есть бэкапы и доступ по API.

```
                 ┌────────────────────────────┐
                 │   Supabase (единая БД)      │  ← источник правды
                 │   лиды · оплаты · анкеты ·  │
                 │   клиенты · вакансии · логи │
                 └──────────┬─────────────────┘
        ┌──────────────┬────┴───────┬──────────────┐
        ▼              ▼            ▼              ▼
   A. okoteam.top   B. oko-agents  C. oko-app   Админка
   (лендинги,       (парсинг+       (продукт     (одна на всех,
    формы,           отклики+        приложение)  на Supabase)
    приём оплат)     диалоги)
```

Что меняется по трекам:
- **A (PHP-сайт):** оставить как есть визуально, но `saveLead`/`saveAnketa`/
  `confirmPayment` перевести с JSON-файлов на запись в Supabase (REST). Медиа
  анкет — в S3 `oko-media`, а не base64 в JSON. Это заодно закрывает п.7 из
  SECURITY_FIX. Срок: ~1 день.
- **B (агенты):** выкинуть собственную SQLite-схему, `models.py` заменить на
  клиент к Supabase. Сфокусировать первый релиз на Волне 1 (см. ниже) на
  **одном** аккаунте, малом объёме, честной легенде «ассистент OKO».
- **C (приложение):** остаётся ядром продукта. Агенты (B) и сайт (A) — это
  каналы привлечения и обслуживания, которые кормят ту же БД.

## Что решить тебе (2 вопроса)

1. **oko-agents заменяет PHP-логику okoteam.top или живёт рядом?**
   Рекомендация: рядом. Сайт — точка входа/оплат; агенты — исходящий канал.
   Общая БД = Supabase.
2. **SQLite в oko-agents — оставляем для оффлайн-MVP или сразу на Supabase?**
   Рекомендация: сразу Supabase, чтобы не мигрировать потом и не расщеплять
   данные о клиентах.

## Порядок работ (предложение)

1. 🔴 SECURITY_FIX.md — сегодня (независимо от всего).
2. A → Supabase: перенос `saveLead/saveAnketa/confirmPayment`, медиа в S3.
3. B Волна 1: `filter` (готов, см. wave1/) → `response` (Claude) →
   `sender` (1 аккаунт, dry-run) → диалог. Всё пишет в Supabase.
4. B Волна 2/3 и C — по плану vault/планы/волны-запуска.
