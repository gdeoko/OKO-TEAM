# Сборка Системы Роста из приложения OKO — runbook для чата «❇️ СИСТЕМЫ ОКО»

Человек в приложении заполняет анкету и жмёт «Собрать систему». Задача уходит
в очередь моста. Этот чат её забирает, проводит анализ и собирает персональную
Систему Роста — один самодостаточный HTML — и кладёт обратно, чтобы она
открылась у человека в аккаунте.

Источники, на которых всё построено: ТЗ «Система Роста OKO TEAM v3.0 ФИНАЛ»
(30 частей), готовые клиентские системы-эталоны и конвейер агентов
(`/workspace/oko-agents`, `ETALONS.md` раздел «Конвейер сделки»).

---

## 1. Цикл работы

```bash
export OKO_QUEUE_TOKEN=...            # уже в Environment variables окружения

# 1. Забрать задачи на сборку систем
node oko-app/tools/oko-queue.mjs pull 3 system

# 2. Собрать (см. разделы 2-5 ниже). Промежуточные отчёты в чат.

# 3. Отдать готовую систему человеку
node oko-app/tools/oko-system.mjs put <task_uid> <файл.html> \
     --title "Система Роста · Имя" --niche "ниша" --period "90 дней"

# Не получилось — честно:
node oko-app/tools/oko-queue.mjs result <task_uid> failed '' 'причина'
```

`oko-system.mjs put` сам: заливает HTML в хранилище, привязывает к задаче,
переводит её в `done` и кладёт в результат ссылку на систему. Приложение
показывает уведомление и открывает систему у человека.

---

## 2. Что приходит в задаче

В `payload` задачи лежит:

| Поле | Что это |
|---|---|
| `anketa` | Ответы на анкету: 37 полей, 10 блоков (О тебе, Продукты, Аудитория, Финансы, Площадки, Объём контента, Формат и стиль, Материалы, Конкуренты, Технические) |
| `profile` | Ник, имя, тариф, дата регистрации |
| `socials` | Привязанные соцсети с реальными счётчиками, если человек их привязал |
| `mode` | `fast` (11 вопросов) или `full` (37) |
| `period` | Период системы: 30 / 90 / 180 / 365 дней |

Чего в анкете нет — **не выдумывать**. Ставить `[УТОЧНИТЬ: цвет бренда]` и
перечислять недостающее в конце системы отдельным блоком «Что уточнить».

## 3. Анализ перед сборкой (порядок обязателен)

Повторяет конвейер агентов, но без КП — владелец просил КП сюда не включать.

1. **Разбор анкеты.** Зафиксировать переменные: имя, ниша, период, цвета,
   продукты, аудитория, соцсети, цели, конкуренты, реквизиты, кодовые слова.
2. **Карточка клиента.** Из свободного текста вытащить: соцсети, сайт, нишу,
   боли, цели, бюджет, город, страну, язык. Логика — `core/client_card.py`
   в репозитории агентов.
3. **Живые счётчики.** Публичные данные соцсетей без логина, под краулерским
   UA (`core/social_scan.py`). Заходить под логином с серверного адреса
   запрещено — потеряем профиль.
4. **Пул конкурентов.** Поиск кандидатов по нише, 4 запроса (2 русских,
   2 английских), до 60 кандидатов на 10 мест (`core/competitor_pool.py`).
5. **Жёсткий отсев.** Оставляем ровно **10 конкурентов**, у каждого **3 ролика
   от 1 000 000 просмотров**, цифры перепроверены на странице ролика.
   Округление YouTube помечаем `approx` и рисуем «≈ 44 млн». Недобор не
   прячем — пишем честно.
6. **Разбор конкурентов.** По каждому: аудитория, позиционирование, воронка,
   монетизация, что работает, что слабо, **что берём себе**. По каждому ролику:
   хук, раскадровка, расшифровка, удержание (подписать как оценку), CTA,
   идея обложки, почему выстрелил.
7. **Генерация содержания разделов** — это и есть основная работа.
8. **Сборка HTML** и отдача через `oko-system.mjs put`.

## 4. Что внутри системы

**Главная.** Hero с именем и периодом, прогресс периода от даты старта,
блок «Сегодня» (тема контента на сегодня + топ-3 задачи), быстрые действия,
сводка-плитки по разделам, ключевые цели из анкеты.

**Контент-план — календарь.** Готовый компонент лежит в
`oko-app/docs/templates/content-calendar.html` — бери его целиком и подставляй
данные в `CP_DATA` и цвет бренда в `--cp-accent`. Он уже проверен: сетка семь
колонок, панель дня, полный текст, кнопка «Копировать», обе темы, гаснет при
`prefers-reduced-motion`. Три уровня раскрытия:
- сетка месяца: 7 колонок по дням недели, в ячейке номер дня, число единиц
  контента и точка-индикатор;
- клик по дню открывает список единиц: иконка формата, тема одной строкой,
  бейдж типа (виральный / кодовое слово / лид-магнит);
- клик по теме открывает **полный текст** целиком плюс кнопки: «Копировать
  текст», для стокового формата — «Промпт для фона», для карусели — «Копировать
  слайды».

Форматы Ф1–Ф8 плюс карусель, пост в Telegram, сторис С1–С5.
**Правило тёплого окружения:** продающий ролик всегда между виральными,
два продающих подряд не ставим.

**Бизнес-план.** Отдельными страницами, не простынёй: Точка А, Финансовая
модель, Продуктовая линейка, Воронка продаж, KPI и метрики, Команда и роли,
Каналы и трафик, Партнёрства и удержание, Риски. В каждом блоке 5-7 секций
со своей инфографикой.

**План действий.** Точка А → цели (6) → боли (6) → шаги (10, у каждого срок,
что делаем, список работ, результат) → дорожная карта (5 вех) → воронка с
числами → сравнение «было/стало» → гарантии → что нужно от клиента → Точка Б.

**Анализ конкурентов.** Карточками, не таблицей: шапка с аватаром и
подписчиками, кнопки площадок (только живые ссылки), раскрывающийся разбор,
столбики просмотров, по каждому ролику полный разбор, в конце «Что берём себе».

**Перспективы.** Дорожная карта на 12 месяцев, сценарии роста (осторожный,
базовый, сильный), масштабирование, новые продукты, позиционирование через
3 года.

**Плюс:** чек-лист по дням, материалы (брендбук, скрипты, промпты), визуал,
трекеры (человек вносит свои числа, система считает производные).

## 5. Дизайн и моушен

- Один файл: весь CSS и JS внутри. Снаружи только шрифты и иконки.
- Тёмная база OKO (`#050505`), акцент — цвет бренда клиента из анкеты,
  запасной лайм `#9AFF00`.
- Canvas-фон с частицами и двумя световыми пятнами на всех страницах.
- Иконки — инлайновый SVG в stroke-стиле, 24×24, stroke-width 1.7.
  **Эмодзи в интерфейсе запрещены.**
- Появление секций при прокрутке, счётчики докручиваются, кольцевые
  индикаторы заполняются, по линии графика бежит огонёк (`animateMotion`).
- Кнопка «Назад» на каждой подстранице, сверху и снизу.
- Mobile-first: человек смотрит с телефона.
- Всё движение гаснет при `prefers-reduced-motion`.

## 6. Жёсткие правила (нарушение = брак)

1. **Ни одного выдуманного числа.** Есть ответ клиента — считаем арифметику и
   показываем формулу. Нет — блок честно говорит, какого ответа не хватает.
2. **Метрики только из реальных источников.** Подписчики, просмотры, реакции,
   даты — из скрапера. Хук, раскадровка, удержание — наш разбор, удержание
   подписывается как оценка.
3. **Никаких обещаний от несуществующей команды.** Формулировки вида
   «аналитик изучает нишу 40 минут» — ложь интерфейса, они уже вычищались.
4. **Длинное тире не ставим никогда**, только дефис. Без канцелярита
   («важно отметить», «комплексный подход», «в кратчайшие сроки»),
   без противопоставлений «не X, а Y». Обращение по имени.
5. **Мёртвые ссылки не показываем.** Проверять содержимое, а не код ответа:
   сервер отдаёт приложение на любой несуществующий путь со статусом 200.
6. **Персональные данные** (паспорт, банковские реквизиты, адреса) в систему
   не попадают.
7. **КП не собираем** — решение владельца.

---

## 7. Сроки

Ориентир полной сборки — **3-6 часов** работы сессии. Приложение показывает
человеку честный статус «в сборке» и не рисует поддельный прогресс: пока
результат не пришёл с сервера, никаких «готово».

Если работа занимает больше — это нормально, статус остаётся «в сборке».
Если не получается совсем — `failed` с человеческой причиной, приложение
покажет её и предложит написать в поддержку.

---

## 8. После сборки

`oko-system.mjs put` делает всё сам:
- система сохраняется в хранилище (`app_systems`) и получает постоянный адрес
  `okoteam.top/api.php?action=oko_system_get&uid=<uid>&raw=1`;
- задача переводится в `done`, в результате лежит ссылка;
- владельцу падает уведомление в Telegram;
- приложение при следующем опросе показывает человеку уведомление, открывает
  систему в разделе «Система роста» и заводит рабочий чат с менеджером.
